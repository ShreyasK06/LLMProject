# Design: BPE tokenizer, faster inference, and a portfolio-ready repo

Date: 2026-10-23. Repo: `ShreyasK06/LLMProject` (own repo, `origin`). Owner: Shreyas.

## Intent and why

This began as a class project: pretrain a small GPT from scratch on a text dataset and prompt it. Shreyas extended it into a chat model on Databricks Dolly 15k with a React front end and a Vercel back end. It is now going on their GitHub as a portfolio piece, so a reader (recruiter, hiring manager, engineer) should conclude in the first minute that the author understands how LLMs and transformers work and built one themselves.

Two problems with the current deployed chat model:

1. **Answers make no sense.** The spelling is fine; the content is not. Cause (hypothesis, to be tested by the experiment below): at 2.9M characters the model spends its capacity learning spelling and word boundaries one character at a time and never reaches word-level structure.
2. **Replies are slow.** The server runs the 10.88M-parameter model in plain JavaScript, one character per forward pass, and a cold start reads 43.5 MB of weights.

## Decisions already made (by Shreyas)

- The model stays **trained from scratch** on the **same Dolly data**. No pretrained weights, no extra data.
- Move from character tokens to **subword (BPE) tokens**. The switch and its measured effect are a headline of the README.
- The README states this started as a class project that the author chose to extend.
- The repo should look professional, and answers and speed should both improve.
- The Shakespeare model stays in the repo as the original class version; the deployed app serves the chat model.

## Goals

1. **BPE tokenizer written by us** (byte-level or character-level BPE, learned on the Dolly training split only, vocabulary around 2,000; exact size left to the builder). Implemented in Python for training and in JavaScript for the server, with a parity test proving identical token ids on a fixed set of strings including edge cases (unicode, empty, long text).
2. **Retrain the chat model with BPE** on the same data and the same split as the character-level models, with a training script Shreyas runs on their GPU machine. The model size must suit about 0.7M training tokens, so smaller and more regularized than the current 10.88M model is expected.
3. **A fair comparison.** Report character-level and BPE models on one metric both can produce: bits per character (total negative log likelihood on a split divided by the number of characters in that split). Report train, validation and test and state which split each number comes from. Keep selection on validation and touch test once.
4. **Faster inference, measured.** Benchmark characters per second and time to first character before and after, on the same prompts. Only claim speedups that were measured. Candidates: cheaper GELU, no per-token string building, cheaper sampling, a smaller model, 16-bit weights on disk, fewer tokens per reply (BPE does this by itself), and a shorter default reply length.
5. **Repo cleanup and README.** Shorter, clearer README (see below), consistent layout, tests that pass, no stray files, and a working local quick-start.

## Non-goals

- Adding data, fine-tuning a pretrained model, or claiming factual correctness. Answers should become more fluent and on-topic, not correct.
- Redesigning the chat UI (it was redone recently).
- Moving off Vercel and GitHub Pages.

## Anti-goals (failure even if it technically works)

- A README that overclaims, or numbers that cannot be reproduced from the repo.
- Breaking the deployed app, or shipping a tokenizer whose JavaScript and Python versions disagree.
- A speed claim without a before/after measurement.
- Reporting one flattering number without its held-out counterpart.

## Constraints

- **No GPU on the dev machine.** Local PyTorch is CPU-only (2.11.0+cpu). Everything is smoke-tested locally on tiny configs; real training happens on Shreyas's GPU machine via scripts we write. Results from that machine must be fed back into the repo (JSON results, logs, exported weights).
- Windows 11 dev machine; Git Bash and PowerShell. Docker and `gh` are not installed. Use venv and local processes.
- Front-end: never hard-code absolute asset paths (use `import.meta.env.BASE_URL`); do not run a production build over a running dev server sharing the output directory.
- Git: no Claude attribution of any kind in commits or PRs. Commits and pushes happen only when Shreyas asks.
- `data/dolly_chat.txt` and `data/dolly_raw.jsonl` are git-ignored and regenerated by `prepare_dolly.py`; any tokenizer or split logic must be deterministic from that script's output.
- Keep the existing deployed model working until a better one is validated, then swap `web/model/` in one change.

## README shape (decided: what, not wording)

Opens with a one-paragraph summary and the class-project origin. Then: how it works (next-token prediction, the architecture, KV cache), the tokenizer story (characters then BPE, with the measured comparison), results with honest limits (single seed unless more are run, different splits explained), how to run it, and repo layout. Architecture and results diagrams are welcome; marketing language is not.

## Left to the builder

Vocabulary size, model dimensions and context length, regularization, how many seeds, the inference optimizations to keep, file layout and naming, licence file, and test structure, as long as the goals and anti-goals above hold.

## Facts about the current code (for the builder)

- **Chat format:** each example is `User:\n<instruction>\n\nAssistant:\n<response>\n\n` (`prepare_dolly.py`). A reply ends at the first blank line. Examples are ASCII-only and shuffled with seed 0 *before* `train.py` takes a sequential 80/10/10 split by position in the text. The BPE models must use the identical text and the same split points (cut at the same example boundary, or as near as token alignment allows, and say which).
- **Baseline numbers:** `dolly_large` 0.8931 / 1.0646 / 1.0602 nats per character (train/val/test) came from `train.py`'s own evaluation on that split, so they already are per-character and convert exactly to bits (divide by ln 2). The checkpoints (`*.pt`) and `data/dolly_chat.txt` are git-ignored and absent from this machine, so the baseline cannot be re-evaluated locally; use the stored numbers and re-run only if the GPU machine has the checkpoint.
- **Current serving path:** `web/lib/gpt.js` loads `web/model/weights.bin` plus `model.json` (config, character list, tensor index) and works on character ids; `export_weights.py` writes both.

## Calls made while writing this (builder-check answers; change any you disagree with)

1. **Tokenizer ships as a data file.** `web/model/tokenizer.json` (merges and vocabulary) is written by the Python trainer and loaded by `gpt.js` at runtime. `gpt.js`, `model.json` and the export format may change. Order of work: Python tokenizer, JS tokenizer with parity test, then model training, then swap.
2. **Chat markers are ordinary text.** `User:`, `Assistant:` and the blank-line stop are not special tokens, which keeps the data and format identical to the character-level runs. The server keeps its existing stop-string logic, applied to decoded text. A single reserved end-of-reply token is an optional later refinement.
3. **Byte-level BPE with a simple pre-split.** Merges never cross a whitespace-to-word boundary, using a hand-written splitter on ASCII classes (no unicode-category regex), so Python and JavaScript agree exactly. The data is already ASCII-only, which makes this safe.
4. **Bits per character** = total negative log likelihood on the split divided by the number of raw characters in the same text span. Special tokens are not used, so the character count is just the length of the text.
5. **Two phases around the GPU.** Phase one is everything buildable and testable here (tokenizer, parity test, training and export scripts, inference speedups with a CPU benchmark, cleanup, README with clearly marked placeholders for training results). Phase two starts when Shreyas returns the training outputs (results JSON, logs, exported weights); then the README numbers are filled in and the weights swapped. Speed numbers state the hardware and Node version they were measured on, and the benchmark is run locally against the Node handler.
6. **Size and speed targets.** The new weight file should not exceed the current 43.5 MB and should be smaller if the model allows (16-bit storage is acceptable if parity with float32 outputs is tested). "Faster" means a measured improvement in characters per second and time to first character against the current build; no fixed threshold.
7. **Cleanup rule.** Files that back a number in the README (`*_results.json`, `logs/`, sample outputs) stay, but move into a `results/` folder with the README links updated. `generate_output.txt` (from the overfit first run) and `run_experiments.sh` stay if they are referenced by the README. Nothing is deleted without checking whether it is referenced.

## Success looks like

- BPE chat model with a better held-out bits-per-character than the character-level `dolly_large` (0.89/1.06/1.06 nats per character train/val/test, which is about 1.29/1.54/1.53 bits per character), or an honest write-up if it does not beat it.
- Replies visibly faster in the web app, with the numbers in the README.
- `npm test` and the Python tests pass from a clean clone.
- The repo reads as one author's coherent, well-explained project.
